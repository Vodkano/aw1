## 0.1.0.1-SK — Entidad, capas de pre-procesamiento, memoria hibrida

### Lo que dice el documento, en una frase

AW1S no es "un prompt a un modelo": es una entidad con estado, compuesta por
varios componentes coordinados, donde tres capas (Inteligencia, Contexto,
Humanizacion) preparan y despues visten lo que hace el componente central
(Procesamiento principal), y todo pasa por una memoria persistente hibrida
(Postgres + pgvector).

### Componentes y responsabilidad de cada uno

| Componente | Recibe | Decide / hace | Entrega |
|---|---|---|---|
| **Inteligencia** | input crudo + metadata de la interaccion | clasifica el problema; decide QUE informacion hace falta, DONDE buscarla y CUANTO; puede iterar (pedir mas busquedas si no alcanza) | una "necesidad de informacion" estructurada |
| **Contexto** | la necesidad de informacion que arma Inteligencia | recupera, filtra y organiza esa informacion desde la memoria (Postgres y/o pgvector) | el contexto ya armado, listo para el modelo |
| **Procesamiento principal** | consulta + instrucciones + contexto ya armado (nunca memoria cruda completa) | resuelve el problema | un resultado interno |
| **Humanizacion** | el resultado interno | lo adapta a una respuesta coherente para el usuario, sin tocar el razonamiento | la respuesta final |
| **Memoria** | el resultado + lo que paso en la interaccion | decide que se guarda y que se vectoriza | persistencia para la proxima vuelta |

Principio explicito del documento, textual porque importa como regla de
diseno: **"el modelo recibe lo que necesita, no todo lo que existe."** Esto
es lo que separa a AW1S de mandarle todo el historial/memoria a un LLM y que
el filtre — aca el filtrado es un paso previo, hecho por Inteligencia +
Contexto, no por el modelo principal.

### Flujo (tal cual lo describe el doc)

```
Entrada
  → Inteligencia (analiza y clasifica)
  → Inteligencia (identifica que informacion falta)
  → Contexto (recupera desde memoria: Postgres / pgvector / ambos)
  → Contexto (construye el contexto final)
  → Procesamiento principal (resuelve)
  → Humanizacion (redacta la respuesta)
  → Memoria (almacena resultado + genera embeddings si corresponde)
```

Con un detalle importante: el tramo "Inteligencia → Contexto" no es
necesariamente una sola pasada. El documento permite ciclos:
`analizar → determinar necesidad → buscar → evaluar → buscar de nuevo si no
alcanzo → recien ahi construir contexto y procesar`. O sea, Inteligencia
puede rechazar lo que trajo Contexto y pedir otra vuelta antes de dejar
pasar el problema al procesamiento principal.

### Que datos ve Inteligencia de cada interaccion

Input/mensaje del usuario, contexto disponible, historial relevante,
metadata de la interaccion, hora/fecha, IP (cuando corresponda y sea
legitimo obtenerla), ID de usuario (si existe), ID de sesion, y "otros datos
tecnicos disponibles del input" (sin especificar cuales — punto abierto,
ver mas abajo).

### Memoria: modelo de datos (entidades conceptuales)

El documento define 7 entidades relacionadas por ID, no un schema SQL
todavia. Las anoto con su relacion probable para cuando haya que bajarlas a
tablas:

- **Usuario** — identifica a la persona cuando es posible (no siempre: hay
  interacciones sin usuario identificado).
- **Sesion** — agrupa interacciones de una misma sesion. `usuario_id`
  opcional.
- **Interaccion** — una entrada + su procesamiento. `sesion_id`.
- **Contexto** — informacion contextual asociada a una interaccion.
  `interaccion_id`.
- **Memoria** — lo que AW1S decide conservar mas alla de la interaccion
  puntual (no toda interaccion se vuelve memoria).
- **Embedding** — representacion vectorial de una Memoria o contenido
  recuperable por significado. Siempre referencia al registro original
  (`memoria_id` u otro), **nunca es la fuente de verdad**.
- **Evento** — acciones/acontecimientos relevantes del sistema (no de la
  conversacion en si — mas cerca de un log de dominio).

Reglas de diseno explicitas que van a condicionar el schema:

1. Postgres es la unica fuente de verdad. Todo lo estructurado
   (identificadores, timestamps, estados, relaciones, metadata,
   clasificaciones) vive ahi directo, sin pasar por vector.
2. pgvector vive DENTRO de Postgres — no hay base vectorial aparte. Decision
   explicita para no sincronizar dos sistemas.
3. No todo se vectoriza. Solo lo que tiene sentido recuperar por
   significado (ciertas memorias, contexto, historial relevante) — el
   documento no da la regla exacta de que califica, otro punto abierto.
4. Cada embedding apunta a su registro original por ID. El dato crudo
   siempre gana; el embedding es solo mecanismo de recuperacion.

### Separacion de responsabilidades (por que importa)

El documento remarca varias veces el limite entre capas porque es la parte
que mas se presta a mezclarse mal en la implementacion:

- Inteligencia decide **que** hace falta. Contexto **no** decide eso, solo
  ejecuta la recuperacion y la organiza.
- Procesamiento principal **no** decide que informacion usar — la recibe ya
  filtrada. Tampoco es tocado por Humanizacion (que no cambia el
  razonamiento, solo la forma).
- Memoria no es un cache pasivo: participa activamente decidiendo que se
  guarda y que se vectoriza al final de cada ciclo.

### Puntos que el documento deja abiertos (para cuando definas mas)

Los anoto para no perderlos, no para resolverlos yo ahora:

1. **Que modelo entrena Inteligencia y con que metodo.** El doc pide
   "investigar y comparar diferentes metodos de entrenamiento" contra la
   documentacion de los modelos ya en AW1 — es una decision pendiente, no
   una que yo deba tomar sola dado el costo de las APIs de pago que ya
   maneja este proyecto (ver CLAUDE.md: el usuario eligio a proposito
   quedarse con el modelo GPT mas barato).
2. **Que califica como "informacion relevante que se conserva como
   Memoria"** vs. una interaccion que no deja rastro mas alla del historial
   de sesion — falta la regla o heuristica.
3. **Que datos tecnicos del input** entran ademas de los listados
   (IP/ID/hora/etc.) — el doc dice "otros" sin enumerar.
4. **Como convive esto con el AW1 actual** (v3, SQLite/Postgres sin
   pgvector, sin capas separadas de este tipo): ¿es un sistema nuevo, un
   reemplazo del `chat/service.py` actual, o corre en paralelo? Todavia no
   hay nada en el documento que lo diga.

No estoy bloqueando en estos puntos — sigo recibiendo los proximos
