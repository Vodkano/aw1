# AW1S — Planos de arquitectura

## 0.1.0.2 — Atajo semantico (fast path pre-Inteligencia)

Fuente: aporte en conversacion (no documento adjunto), en respuesta directa
al punto de costo operativo senalado en `documentacion/arquitectura.md#7`
(un ciclo completo implica minimo 2 llamadas a LLM por turno).

### La idea, confirmada

Antes de que el mensaje entre a Inteligencia, se compara contra un vectorDB
chico y curado de frases ya conocidas (saludos, despedidas, agradecimientos,
cosas que el sistema ya tiene "memorizadas" como respuesta fija). Si hay un
match suficientemente fuerte, se devuelve la respuesta prearmada asociada
**sin llamar a ningun modelo** — ni Inteligencia, ni Procesamiento
principal, ni Humanizacion. Si no hay match fuerte, el mensaje sigue el
flujo normal completo (ver `arquitectura.md#4`).

Confirmado explicitamente: no es pasar un score como pista al modelo, ni
pasar el embedding como input — es un cortocircuito real. El modelo entra
en juego solo cuando el atajo no resuelve.

### Por que importa

Es la mitigacion directa al costo que hacia pesada a esta arquitectura
comparada con el AW1 actual: la mayoria del trafico conversacional real
son mensajes triviales (saludos, "gracias", chequeos de que el bot esta
vivo) que no necesitan clasificacion ni resolucion — cachearlos evita
2-3 llamadas a LLM por cada uno de esos turnos.

### Como se integra (interpretacion propia — ver puntos abiertos abajo)

```
Entrada
  → Atajo semantico: compara contra el indice de frases conocidas
        → match fuerte: devuelve respuesta prearmada. FIN, no hay LLM.
        → sin match: sigue el flujo normal
  → Inteligencia → Contexto → Procesamiento principal → Humanizacion → Memoria
```

Este indice **no es lo mismo** que la Memoria (Postgres+pgvector) ya
definida en la spec original. La Memoria guarda el historial real de
interacciones de cada usuario/sesion, crece con el uso y es dinamica. El
indice del atajo es chico, curado a mano (o revisado periodicamente), y no
deberia mezclarse con la tabla de Memoria — son dos pgvector distintos con
proposito distinto, aunque tecnicamente puedan vivir en la misma instancia
de Postgres.

### Calibracion (v1 — 0.1.0.2.1)

Resuelve el punto 1 de mas abajo. Regla en tres pasos, cada uno mas caro
que el anterior — se sale del proceso apenas uno autoriza o descarta:

**Paso 0 — filtro de longitud (determinista, sin vectorizar).**
Si el mensaje supera **6 palabras o 40 caracteres**, el atajo ni se evalua:
va directo al flujo completo. Esto por si solo resuelve el ejemplo que
preocupaba ("hola, tengo un problema urgente con mi pedido" tiene 8
palabras) sin depender de ningun score — una frase realmente trivial
(saludo, gracias, chau) es corta por naturaleza; si no lo es, ya dejo de
ser un caso para el atajo.

**Paso 1 — match exacto normalizado (determinista, sin vectorizar).**
Se normaliza el mensaje (minusculas, sin tildes, sin signos de puntuacion,
sin espacios de mas) y se compara contra las entradas del indice tal cual.
Si hay match 1:1 ("hola", "buenas", "gracias", "chau"), autoriza el atajo
directo — cero ambiguedad, no hace falta score.

**Paso 2 — similitud por embedding (solo si el paso 1 no matcheo).**
Se vectoriza el mensaje y se compara por similitud coseno contra el
indice:
- **≥ 0.93** → autoriza el atajo (cubre variantes/typos: "holaa", "buen
  dia", "muchas gracias").
- **0.85 – 0.93** → zona gris: NO autoriza el atajo (sigue el flujo
  completo), pero se loguea como casi-match para revisar despues si el
  indice deberia crecer con esa variante (resuelve el punto 4, mas abajo).
- **< 0.85** → no autoriza, sigue el flujo completo.

**Regla adicional — sesion activa.** Aunque un mensaje pase el paso 0 o 1,
si la sesion tiene una interaccion previa reciente sin resolver (ej. una
consulta abierta en los ultimos minutos), el atajo no se aplica salvo que
la entrada matcheada sea explicitamente de categoria "despedida" (una
despedida SI tiene sentido a mitad o al final de una conversacion real).
Resuelve parcialmente el punto 3, mas abajo.

Los numeros (6 palabras, 0.93, 0.85) son un punto de partida razonable, no
un resultado medido — se ajustan con los casi-match logueados una vez que
haya trafico real.
