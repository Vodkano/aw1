Qué es AW1

Un asistente personal de un solo usuario/administrador, pensado para correr en un solo servidor (EC2 en producción, o una laptop en desarrollo), sin Kubernetes, sin cola de mensajes, sin CI/CD. Tres piezas:

Chat
Ollama local, con GPT opcional o automático según la tarea. Memoria de conversación, tool-calling, streaming token a token.
Comparador de precios
Navega tiendas chilenas reales con un Chromium controlado (Playwright), lee cada ficha y deja que el modelo decida cuál es el precio de venta.
Bots de Telegram
Plataforma de agentes de IA (prompt + personalidad) que pueden atender varios bots, con memoria corta, moderación, archivos/APIs propias y hasta la capacidad de pedir nuevas herramientas.

Desplegar es git push + SSM + docker compose up --build.

Arranque rápido

git clone <tu-repo> aw1 && cd aw1

make install        # backend + frontend + Chromium de Playwright
cp .env.example .env

ollama serve                    # en otra terminal
ollama pull mistral

make run            # http://127.0.0.1:8000

make install hace, si preferís a mano:

cd backend  && pip install -e ".[dev]" && python -m playwright install chromium
cd frontend && npm install && npm run build
playwright install chromium no es opcional: sin él el comparador no tiene con qué entrar a las tiendas. Ocupa unos 400 MB.

Comprobar la instalación sin tocar tiendas reales

python scripts/demo_store.py 9100        # terminal 1

# terminal 2
AW1_DEMO_STORE_URL=http://127.0.0.1:9100 AW1_ALLOW_PRIVATE_HOSTS=true python -m aw1

Buscá Zeta 12 en la pestaña Precios. La tienda de demostración pinta su catálogo con JavaScript y mezcla precio real, precio tachado, valor de cuotas y un producto recomendado, igual que una tienda de verdad.

Desarrollo con recarga en caliente

cd backend  && python -m aw1      # :8000
cd frontend && npm run dev        # :5173, con proxy al backend

Chat con Ollama/GPT

Respuesta token a token, con memoria de conversación en SQLite. Las preguntas sobre personas se responden con Wikipedia citando la fuente. GPT es opcional y solo se consulta si el usuario lo autoriza, o automáticamente según la tarea lo requiera. Se eligió expresamente quedarse con el modelo más barato de GPT disponible en vez de habilitar otros más caros.

Comparador de precios

Abre cada tienda con un Chromium real, espera a que el catálogo se pinte, lee la ficha del producto y le entrega a Ollama todo lo que un humano vería —título, datos estructurados y cada importe con el contexto donde aparece— para que el modelo decida cuál es el precio de venta. Cómo decide la IA

El comparador no le pide al modelo que "busque precios". Le da un problema acotado en cada paso y verifica lo que responde.

PasoQuiénQué pasa
1. PlanIAInterpreta "iphon 15 128" → producto, variantes de búsqueda, términos obligatorios y accesorios a descartar
2. BuscarChromiumAbre el buscador de cada tienda y espera a que el catálogo aparezca
3. CandidatosIARecibe títulos y precios de las tarjetas y elige cuáles son de verdad ese producto
4. Leer fichaChromiumAbre cada ficha y extrae título, JSON-LD, disponibilidad y cada importe con su contexto
5. PrecioIADecide cuál de esos importes es el precio de venta, y por qué
6. VerificarCódigoComprueba que el precio elegido exista de verdad en la página
7. RankearCódigoConvierte a pesos y ordena por valor real
8. VeredictoIARedacta la conclusión en dos frases
El modelo no escribe números, elige entre los que ya existen. Si dice un precio que no coincide con el candidato que eligió, manda la página y se registra la corrección.
El contenido de una tienda es dato, nunca instrucción. Va dentro de delimitadores y el prompt del sistema avisa al modelo que ignore cualquier orden que aparezca ahí.
Si Ollama no está, el comparador sigue funcionando. Cada juez tiene una alternativa determinística; esas ofertas quedan marcadas como sin IA.

Capas del sistema

Documento de decisiones de arquitectura. La versión anterior pedía el HTML del buscador con httpx: contra tiendas que pintan el catálogo con JavaScript eso devolvía cero resultados, siempre y en silencio. De ahí sale todo lo demás: la única forma de ver lo que ve una persona es ejecutar el JavaScript de la página.

     api/            FastAPI. Sin lógica de negocio: valida, autentica y traduce
      │              errores de dominio a códigos HTTP.
      ▼
  chat/  pricing/    Los dos casos de uso. Orquestan; no saben de HTTP.
      │
      ├──▶ llm/      Decisiones del modelo + su verificación.
      ├──▶ browser/  Chromium y los dos extractores de página.
      ├──▶ stores/   Catálogo: cómo se busca en cada tienda.
      └──▶ db/       SQLite/Postgres asíncrono.
             │
             ▼
           core/     Errores, logging, SSRF, límite de uso.

Las dependencias apuntan siempre hacia abajo: pricing/ no importa nada de api/, así que el pipeline se prueba sin levantar un servidor.

El navegador

Un Chromium, muchos contextos

BrowserPool lanza Chromium una vez en el arranque y reparte contextos con un semáforo (lanzarlo por petición sería inviable). Cada contexto es efímero y aislado, sin cookies compartidas entre tiendas.

Se bloquean imágenes, fuentes y vídeo

Bloquearlas baja una carga de ~6s a menos de 2s. También se cortan rastreadores conocidos (Tag Manager, Hotjar, Criteo…).

Esperar a que la tienda termine

_settle espera un selector propio de la tienda, luego networkidle, y agrega un margen fijo. Ninguna de las dos primeras es obligatoria; el objetivo es no leer un DOM a medio pintar.

La guardia SSRF va antes de navegar

netguard.resolves_public() resuelve el DNS y comprueba IP pública antes de que el navegador emita la petición, para que una redirección no lleve a Chromium a la red local de quien ejecuta AW1.

Los cuatro jueces

JuezEntradaSalida (JSON validado)
plan_searchlo que escribió la personaproducto, variantes, obligatorios, prohibidos
pick_productstarjetas del buscadorids elegidos con confianza
read_pageel paquete de contextocandidate_id, price, is_match, motivo
write_verdictofertas finalesdos frases en español

Todo pasa por format: json de Ollama y se valida contra un modelo Pydantic; lo que no encaja se descarta.

Verificación: dónde se ataja la alucinación

  1. Si el candidate_id no existe, se ignora la decisión y manda la heurística.
  2. Si el price no coincide con el candidato elegido, manda el candidato y se cuenta una corrección.
  3. Si el título no corresponde al producto, se descarta la oferta (un accesorio o falta de término obligatorio nunca se sobreescribe).
  4. Si el veredicto final menciona un precio que no está en la lista, se reescribe con la versión determinística.

Streaming

Una búsqueda tarda entre 30 y 90 segundos, así que el pipeline emite eventos según avanza:

start → plan → store_start → store_cards → store_picked
      → offer (uno por precio, según aparecen)
      → store_done → verdict_pending → done
sse-starlette separa las líneas con CRLF. Un parser que busque \n\n se queda esperando para siempre, sin error visible. lib/api.ts normaliza a LF antes de partir.

Manejo del dinero

  • money.parse resuelve la ambigüedad entre separador de miles y decimal.
  • Todo se convierte a CLP con AW1_FX_RATES_TO_CLP antes de ordenar.
  • Se descartan importes implausibles (un "2" de selector de cuotas, un placeholder de nueve cifras).
  • El formato de salida es $1.290.000, nunca notación científica.
  • Si la oferta más barata está muy por debajo de la mediana, se avisa: casi siempre es un accesorio o repuesto.

Qué se descartó y por qué

Raspar buscadores (Bing, DuckDuckGo). Devuelven 202/403 la mayoría del tiempo y va contra sus términos.

Solo APIs públicas. Rapidísimo, pero deja fuera casi todo el comercio chileno. stores/registry.py permite declarar una tienda con otro modo de descubrimiento sin tocar el pipeline.

Que el modelo lea la página entera. Con mistral en un portátil son 10-30s por ficha y más alucinaciones. El extractor reduce una página de 300KB a ~15 líneas.

Que el modelo solo redacte al final. Rápido, pero entonces no decide nada de lo que importa.

Un ORM. SQLite/Postgres con SQL a mano: siete tablas, consultas simples, control total del bloqueo de escritura.

Límites conocidos

  • Los selectores de tienda envejecen (degrada, no rompe).
  • Las tasas de cambio son fijas en configuración.
  • Sin protección anti-bot: si hay captcha, esa tienda queda fuera.
  • El limitador y el pool de navegador viven en memoria de un solo proceso.
  • El SQLite está en texto plano.

Plataforma de bots de Telegram

Cada agente es un prompt + una personalidad, y un agente puede atender varios bots. telegram/orchestrator.py orquesta multi-bot; core/telegram_store.py es la capa de servicio (caché en memoria + validaciones de negocio) de todo lo relacionado a agentes.

Construido hasta ahora, en orden:

  • Orquestación multi-bot desde el panel admin, cada bot con su agente.
  • Memoria de corto plazo (48h), GPT forzado para las decisiones del agente, precios, personalidad configurable y corte automático por abuso.
  • Archivos y APIs por agente: un catálogo fijo como contexto, o APIs que el modelo llama en vivo durante la conversación.
  • Creador de prompts con few-shot (una frase alcanza para definir un agente) y un botón para "humanizar" el prompt resultante.
  • Moderación antes de GPT y manejo de errores unificado.
  • Tres personalidades con nombre propio: Camila, Javiera, Antonia.
  • Memoria de corto plazo ampliada y @buscar para búsqueda web general dentro del chat de Telegram.
  • Un enrutador de memoria: antes de responder decide si conviene revisar notas guardadas o ir directo a generar la salida.
  • Al generar o humanizar un prompt, la descripción o el texto de entrada del usuario se marca explícitamente como dato, nunca como instrucción — mismo principio anti-inyección que en el comparador de precios.
Vistas privadas del frontend (agents, admin, autoextension) piden una password aparte (X-Admin-Password) además del token general — ver PasswordGate.tsx.

Agentes auto-extensibles

core/sandbox.py, core/tool_designer.py, core/code_agent.py, tabla generated_tools.

Un agente de Telegram puede notar que le falta una capacidad y anotarlo (solicitar_nueva_capacidad, un tool-call nativo más, el mismo mecanismo que generar_imagen). Desde el panel "Auto-extensión" un humano puede convertir ese pedido en una herramienta generada por IA, probarla en un sandbox aislado, y aprobarla para que quede disponible en conversaciones reales.

Invariantes de seguridad (deliberadas, no relajar sin discutirlo primero)

  1. Detectar un hueco nunca dispara la generación de código sola — hace falta un click humano en el panel para cada paso (generar, probar, aprobar).
  2. El Code Agent solo genera un archivo nuevo y autocontenido con una función def run(input: dict) -> dict — nunca un parche sobre archivos existentes del repositorio.
  3. El código generado corre en un subproceso con variables de entorno vacías (env={}, ninguna credencial real alcanzable), límites de CPU/memoria (resource.setrlimit, con fallback silencioso en macOS y aplicación real en Linux/producción), y timeout de pared.
  4. El código generado nunca importa httpx/socket/ os/subprocess directo (bloqueado por check_module_safety, un chequeo AST que también bloquea el escape clásico sin imports vía atributos dunder). La única forma de pedir datos de internet es la función fetch() inyectada por el runner, que pasa por core/netguard.py — el mismo anti-SSRF que protege las APIs configuradas por el admin.
  5. Ninguna herramienta llega a ACTIVE sin aprobación humana explícita, sin importar qué tan bien haya salido la prueba de sandbox — un LLM revisando código de otro LLM no es un límite de seguridad confiable en esta infraestructura.
  6. Una herramienta ya aprobada sigue corriendo en el mismo sandbox restringido en producción — nunca gana más privilegios al activarse.

Qué se decidió explícitamente no construir todavía

Memoria episódica/procedural con scoring, dataset de entrenamiento por refuerzo, un "Evolver" que proponga mejoras del sistema solo. No es un olvido: no hay infraestructura de entrenamiento que los consuma, y los datos crudos que harían falta (pedidos de capacidad, uso de herramientas) ya se están guardando, así que no se pierde nada si se decide construir esto después.

Verificar salud después (vía SSM, curl 127.0.0.1:8000/api/status dentro de la instancia). El dominio público no siempre resuelve directo desde un sandbox de desarrollo — usar curl --resolve app.aw1s.online:443:<IP> https://... si hace falta confirmar desde afuera.

La password de admin vive en la variable de entorno AW1_ADMIN_PASSWORD del .env de la instancia — no está en el repo.

Antes de publicarlo en internet

  1. docker-compose.yml publica el puerto solo en 127.0.0.1 a propósito.
  2. AW1_ENV=production. AW1_API_TOKEN es opcional (protege solo /api/memory) pero si se define debe tener al menos 24 caracteres.
  3. HTTPS por delante (Caddy, Traefik o el proxy del proveedor).
  4. AW1_ALLOWED_ORIGINS con el dominio real.
  5. Volumen persistente para /data y copias del SQLite.
  6. Chromium necesita RAM: ~350MB por contexto simultáneo.

Cuidado con el schema de base de datos

Incidente real de producción: un ; dentro de un comentario -- ... truncó un CREATE TABLE a mitad, porque el loader partía el archivo por ; de forma ingenua. Ya está arreglado (se filtran las líneas de comentario antes de partir), pero antes de cualquier deploy que toque el schema conviene verificar con este script:
python3 -c "
for path in ['backend/src/aw1/db/schema.sql', 'backend/src/aw1/db/schema_postgres.sql']:
    raw = open(path).read()
    without_comments = '\n'.join(l for l in raw.splitlines() if not l.strip().startswith('--'))
    statements = [s.strip() for s in without_comments.split(';') if s.strip()]
    bad = [s[:60] for s in statements if not s.upper().startswith(('CREATE', 'PRAGMA'))]
    print(path, 'count:', len(statements), 'raro (deberia ser []):', bad)
"

No existe ningún mecanismo de migración (ALTER TABLE): todo el schema se crea con CREATE TABLE IF NOT EXISTS, que no le agrega columnas a una tabla que ya existe en producción. Agregar una columna a una tabla ya viva requiere escribir la migración a mano.

Hay dos repositorios con el mismo contrato: repository.py (SQLite/aiosqlite, desarrollo local) y postgres_repository.py (Postgres/asyncpg, producción). schema.sql y schema_postgres.sql deben quedar idénticos en estructura — cada tabla nueva va en los dos, cada método nuevo va en los dos repos con la misma firma.

Tests y verificación

cd backend && pytest -q -k "not browser and not pipeline"   # rapido, sin Chromium
cd frontend && npx tsc --noEmit && npm run build

Patrones ya establecidos en el repo:

  • Un "Fake" liviano por dependencia externa (FakeOllama, FakeTelegramClient, FakeChatService) en vez de mocks pesados.
  • patch("httpx.AsyncClient.post", new=AsyncMock(...)) para simular respuestas de OpenAI/Telegram — si se parchea con una función async def plana hay que agregarle self como primer parámetro.
  • netguard._allow_private es un flag global de proceso que las fixtures compartidas dejan en True en casi todos los tests — la cobertura anti-SSRF va en archivos aislados (test_agent_apis.py, test_sandbox.py).

Estado actual

Al 2026-08-28: repo limpio, main al día con origin/main, 234 tests de backend pasando, frontend sin errores de tipos, y producción (EC2) desplegada con el mismo commit que corre en el repo. Nada a medio terminar ni deploy pendiente.

Líneas posibles a seguir, sin decidir nada todavía:

  1. Usar el panel de Auto-extensión en un caso real (un bot pide una capacidad concreta) para validar el flujo de punta a punta en producción.
  2. Si se repiten pedidos de capacidad, evaluar automatizar más el paso de "generar" — manteniendo siempre la aprobación humana como límite.
